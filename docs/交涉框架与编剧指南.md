# 交涉框架与编剧指南

对白、人物声线、内心活动与错误反馈的完整写作约定见 [《文案设计规格》](文案设计规格.md)。本文重点说明交涉编排与 Ink 实现。

在 Inky 打开 [泊石展务的 story.ink](../content/boshi-pay/story.ink)，从开场后的「预览」菜单进入任一话题，编辑并试玩对白、内心话和选项。合同、附件、举证判定和改稿文字在同目录的 [chapter.ts](../content/boshi-pay/chapter.ts)。Inky 预览时会使用文件末尾的条件函数作为默认值。实际拿到文件或线索之后的分支，请进网页试玩。 [Inky 编辑器](https://github.com/inkle/inky)

## 编排一轮交涉

**从玩家看得见的疑点开口。** 先写下哪句条款或哪处调查结果值得追问，以及答案会怎样影响玩家的决定。条款含糊时，先让主角问具体会怎么执行。有些问题问清了就能结束，这一轮也成立。

**先把双方的算盘算清楚。** 主角想保住哪些条件，手里有什么筹码，谈到哪一步愿意接受？对方想让主角接受什么，哪些信息愿意给，哪些会留着不说，什么得找别人批？对方可以爽快发来需要核对的附件，也可能为了尽快签约，只报一个好听的总数，拿「大家都这样」施压，或者把问题带到容易答的地方。主角也可以追问对方没答的那个条件，或拿已经谈妥的事要求对方写下来。每句答话都要有眼下的理由，双方的承诺和让步也要符合各自的权限与筹码。

**让同一组选项问出不同的事。** 按玩家此刻知道的内容写几句说得出口的回复。问谁负责结算可能问出一份确认单，问排班可以弄清轮值怎么安排，追问只去一次会不会付钱则可能逼对方明确口径。文件要在对方有理由发的时候出现。玩家应当能从前文判断该往哪儿问，走错方向也能听出还缺什么。试玩时，检查玩家能否沿一条有逻辑的路线找到证据，以及提前问到矛盾时能否先放下、补完材料再回来。

**把证据对到同一件事上。** 改编案例时先核清谁按哪份文件执行、哪个版本适用，再把口头说法和原文放进同一个情形。比如林悦说「去一场就算一场」，拟排班能说明哪天要到场，确认单上「做满两次才发」才回答了只去一场能否拿钱。对方给出明确的主张后再开放举证。举证成立时，让主角亲口说清两边各自怎么说、差别会造成什么后果、希望怎么改。对方接下来能让到哪一步，仍取决于前面设定的权限和利益。

**把对白连起来读一遍。** 每句话都要接得上上一句，也要像这个人现在会说的话。用当事人会问的具体问题，把「请明确实际执行口径」写成「第二场要是取消了，我去的那一场还给钱吗？」内心话写主角此刻在怀疑什么、下一步想核对什么，把结论留到举证后由主角说出来。

### 异议、举证与错误反思

将「提出异议」与「提交后的错误反思」分开写，不让界面或角色替玩家提前解题。

1. **提出异议时不使用攻略口吻。** `steps` 中的内心话用于表现主角对当前说法的直觉、疑惑或初步联想，应当从眼前的事实自然生发。不得使用「先找／再找某文件」「选择某条原文」「需要补齐哪项条件」等操作指令，也不得直接公布证据组合或判定结论。可以写「她说关账号不影响申请，可结算页不是也要用工作账号登录吗？」，不写「先找离场流程，再找结算说明」。
2. **举证过程中保持悬念。** 逐段内心话可以随着已确认的原句深化疑问，但应保留玩家自行对照和判断的空间。不得把内心话写成证据槽位说明、任务清单或标准答案。
3. **错误提示只出现在提交之后。** `mistakes` 与 `wrong` 可以给出针对性的引导，但引导应由主角在反思中意识到，并标记为 `# thought`。提示应指出本次引用没有证明什么、遗漏了哪个关键事实，以及可以回到哪类材料重新核对；不得只写「证据不对」「条件没有对齐」等空泛结论。
4. **对方只作符合身份与立场的回应。** 对方可以否认矛盾、指出引文与其主张并不冲突，或对无关材料表示疑惑，但不得代替玩家分析证据链、给出检索步骤或充当教程。对方一句简短回应之后，接主角的具体反思。
5. **出处与事实必须核对。** 内心话、对方回应和反思中提到的文件名称、时间、金额、条件及行为，应与 `documents` 中实际引文一致。不得为了提示流畅，把某项条件归到并未记载它的文件中。多段举证应让每段想法承接当前已确认的内容，而不是预设玩家选择了某条尚未提交的原文。
6. **语气随认知阶段变化。** 异议阶段写「哪里听着不对」，错误反思阶段才写「为什么没有证明、还能怎样核对」。举证成立后，再由主角以 `# player` 明确说清冲突及希望修改的内容。

错误反馈的基本顺序为：对方针对引文作简短回应 → 主角以内心话反思缺漏 → 游戏执行耐心与检查点变化。示例：

```ink
=== wrong_account ===
人走关账号，这没问题。我又没说不让关。
对，关账号本身没错。真正不对的是关的时候，申请还没开。 # thought
-> END
```

## 用 Ink 写对白和选项

用 Ink 的命名段落把对话分开。普通台词默认由对方说，`# player` 是主角说出口的话，`# thought` 是主角的内心活动，界面会加括号。玩家选择由游戏显示为主角台词。

```ink
=== ask_window ===
我想核对一下卧室窗户的状态。 # player
窗框我刚看过，没有水渍。
{has_clue("window"):
    + [我在窗边记下了一处情况。 # choice:show]
        -> window_claim
}
+ [我再回去看看。 # choice:later]
    -> desk
```

用 `+ [选项 # choice:ID]` 写可以重新选择的选项。同一组可见选项的 ID 要唯一，改台词时保留它们以便读档。`has_file("ID")` 和 `has_clue("ID")` 读取游戏状态。在 Inky 中可以临时把对应的备用函数返回值改成 `true`，预览获得材料后的分支，试玩完再恢复。

| Ink 标签 | 作用 |
| --- | --- |
| `# file:ID` | 发出指定附件。连续附件一起送达，游戏等待玩家确认读完。 |
| `# request:ID` | 未收过时发件，已收过时打开现行版。 |
| `# signing:request` / `# signing:review` / `# signing:send` | 领取缺少的签署附件，打开核稿摘要，或在结案时发送现行签署包。三者共用章节的 `signing` 清单。 |
| `# locate:文件ID.原句ID` | 打开已收文件的现行版并定位原句。只写文件 ID 时打开文件。 |
| `# speaker:ID` | 标记群聊发言人。姓名和身份由章节的 `speakers` 配置。 |
| `# proof:ID` | 打开指定举证规则。用 `-> END` 结束该段，由玩家圈选原文。 |
| `# deadlock:ID` | 按指定检查点退回话题并扣耐心。用 `-> END` 结束该段。 |
| `# amend:ID` | 应用指定书面改稿，生成新版本并恢复一点耐心。 |
| `# desk` | 回到阅读和选话题的状态。 |
| `# review` / `# leave` | 打开结束审阅确认框，或在玩家已明确选择不签时直接进入离开结局。 |

## 写文件和举证

在 `documents` 给每份材料和每条可引用原句指定稳定 ID。`initialFiles` 是开局就能看的文件。举证规则放在 `proofs`，用 `文档ID.原句ID` 写出正确组合和常见误读。`steps` 指向逐段出现的内心话，`accepts` 指向主角反驳和后续交涉，`mistakes` 与 `wrong` 指向错误反馈段落。错误反馈段落可包含对方的简短回应和主角的 `# thought` 反思，具体分工见「异议、举证与错误反思」。`anchor: "reply"` 会把对方上一句台词附到对照记录中。

举证的 `back` 以及僵局的回退路线可以按已收材料选择检查点，最后保留一条无条件路线。用于内心话、错误反馈、退回和结案的短段落只写台词、内心话或发文件，末尾用 `-> END`。改稿在 `amendments` 定义。按文件 ID 和原句 ID 给出替换文本，同一句可以在后续不同改稿中再次替换。界面会保留修改前的版本和删除线。

举证需要的原文段数有多种时，在 `minQuotes` 指定最少确认段数，并在 `accepts` 中列出充分的组合。程序会选能被引用覆盖的最长组合。错误反馈可用 `excludes` 指定哪些原文出现时就跳过这条反馈。用 `preserveDraft` 保留沉默前已确认的原文。分支通过 `has_proof("ID")` 检查矛盾是否已证实，通过 `has_amendment("ID")` 检查书面改稿是否已接受。

把发件、定位、改稿等标签单独写在动作应出现的位置。构建会让这些动作按剧本顺序播放。回退检查点只恢复可选话术，索取缺失材料应当有独立选项。结案要跳到哪段原文，可在对应改稿的 `recap` 中配置。

## 接入话题和调查

`topics` 定义话题标签、进入 Ink 的段落和关联的改稿。用 `clauseTopics` 将主合同章节 ID 关联到话题 ID。话题改过后仍可开启，`followUps` 按顺序采用第一个已完成指定改稿的入口。

调查入口可参考 [窗户测试场景](../content/window-demo/chapter.ts)。`floorPlan.hotspots` 的坐标是相对于图片宽高的百分比，`observation` 是玩家点到位置时看到的结果。`files` 可发放用来举证的材料，`topic` 则允许玩家调查后主动开口。合同和调查点可以指向同一个话题。调查和开口分别存档。

新增剧本时，在 `content/<章节 ID>/` 写 `chapter.ts` 和 `story.ink`，在 [章节目录](../content/chapters.ts) 登记一次。首页按目录顺序解锁。待验收章节用 `candidate`，本地可完整试玩，验收后将其设为 `released`。仅用于开发的独立测试用 `demo`，例如本地的 `?chapter=window-demo`。

在仓库根目录运行 `npm test` 检查类型、剧本引用、举证、续关和保存恢复。运行 `npm start` 完整试玩，修改剧本后重新构建。若更改已发布的选项 ID、段落路线或影响重放的内容，提升该剧本的 `revision`。
